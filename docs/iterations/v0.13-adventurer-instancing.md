# v0.13 Adventurer Instancing

## 本次目标

在 `v0.12` 的存档骨架稳定后，先把“冒险者作为长期对象如何存在”正式立起来。

这版要解决的不是：

- 完整随机冒险者生成
- 完整冒险者养成
- 阵营 / 黑化 / 忠诚等后续长期系统

这版要解决的是：

- 当前配置里的冒险者模板，如何和玩家存档中的长期冒险者实例分开
- 哪些字段属于“实例当前正式状态”，必须长期保存
- 哪些字段只需要作为轻量来源锚点保留
- 旧固定冒险者如何在不推翻旧档的前提下并入实例层

换句话说：

- `v0.12` 解决“状态如何正式保存”
- `v0.13` 解决“冒险者本人如何成为可长期保存的正式对象”

## 本次范围

- 正式定义：
  - 冒险者模板
  - 冒险者实例
  - 模板到实例的最小映射关系
- 明确实例最小字段集
- 明确哪些未来字段现在不做，后续通过迁移补值
- 让当前固定冒险者能够被视为第一批实例

## 明确不做

- 大规模随机池刷新
- 完整随机姓名 / 外观 /稀有度系统
- 冒险者成长曲线
- 好感 / 关系深化
- 阵营 / 黑化 / 对立系统
- 市场 / 招募经济系统

## 关键规则

- 当前优先解决“实例边界”，不是“内容量”
- 模板数据继续属于配置层，不直接成为存档主体
- 存档里优先保存实例当前正式状态，而不是生成过程回放
- 生成过程细节可以不保留，但实例不能成为完全无来历黑盒
- 对旧版本里未明确承诺为长期强后果的内容：
  - 可以迁移为倾向
  - 不应直接迁移为强惩罚或强敌对结果
- 新系统上线后的旧档兼容，应优先靠版本迁移和保护性默认值
  - 不默认翻旧账

## 实例最小字段集（当前意向）

- `instanceId`
  - 稳定实例标识，进入存档后不再变化
- `templateId`
  - 轻量来源锚点
- `originType`
  - 当前至少区分：
  - `handcrafted`
  - `generated`
- 当前正式展示与玩法状态：
  - 名称
  - 称号
  - 偏好
  - 人格
  - 正式能力
  - 印象 / 传闻 / 动机等当前已参与展示的字段
  - 已知度与接触状态
  - 当前任务状态
  - 长期关系相关运行时状态
- 当前判断：
  - 不要求保存完整生成扰动明细
  - 不要求保存“为什么长成这样”的过程历史
  - 但保留最少来源锚点，避免后续完全失去兼容抓手

## 当前不预埋的未来字段

- 阵营
- 黑化路线正式状态
- 忠诚 / 背叛正式状态
- 完整成长履历
- 不可逆事件链完整历史

这些字段当前不提前硬塞。

后续如果真的落地，应优先通过：

- 新版本迁移默认值
- 旧记录转倾向而不是直接定案
- 新系统首次接入时再正式确认

来处理旧档兼容。

## 旧固定冒险者并入策略

- 当前 `config/adventurers.json` 里的固定人物，先视为模板来源
- 本版不急着做完整模板库重构
- 先允许它们作为“首批已生成实例”进入运行时
- 旧档读入时：
  - 不要求回放生成过程
  - 只要求能稳定恢复当前实例状态

## 验收标准

- 代码中已能正式区分模板和实例
- 当前固定冒险者不再只能以“模板即实例”的方式存在
- 冒险者实例已有稳定 id 和最小来源锚点
- 新版本继续做随机生成或养成时，不需要再推翻实例骨架

## 风险和待定问题

- 如果模板和实例继续混写，随机系统一进来就会带着存档和成长一起返工
- 如果实例完全不留来源锚点，后续新系统迁移只能靠猜
- 如果现在就预埋太多未来字段，又会把还没定义清楚的系统硬塞进存档骨架

## 跨版本待处理

- 随机冒险者生成
- 实例池刷新规则
- 冒险者成长
- 阵营 / 黑化等强后果系统
- 旧档接入这些新系统时的定向迁移

## 结果记录

- 版本开始时先确认：
  - 下一步不直接做完整随机生成
  - 也不先做完整养成
  - 当前真正的前置工作，是把“长期人物实例”正式立起来
- 当前已确认的设计判断：
  - 玩家更在意“这个人现在是谁”，而不是“当初生成时每一步怎么算”
  - 因此存档应优先保存实例当前正式状态
  - 但完全抹掉来源信息并不稳，至少要保留少量来源锚点
  - 旧版本里只服务文本差异、未明确承诺长期强后果的选择，后续不应被直接追溯成重惩罚
