# v0.13 Adventurer Instancing

## 本次目标

在 `v0.12` 的存档骨架稳定后，先把“冒险者作为长期对象如何存在”正式立起来。

这版要解决的不是：

- 完整随机冒险者生成
- 完整冒险者养成
- 阵营 / 黑化 / 忠诚等后续长期系统

这版要解决的是：

- 当前配置里的冒险者模板，如何和玩家存档中的长期冒险者实例分开
- 哪些字段属于“实例当前正式状态”，必须长期保存
- 哪些字段只需要作为轻量来源锚点保留
- 旧固定冒险者如何在不推翻旧档的前提下并入实例层

换句话说：

- `v0.12` 解决“状态如何正式保存”
- `v0.13` 解决“冒险者本人如何成为可长期保存的正式对象”

## 本次范围

- 正式定义：
  - 冒险者模板
  - 冒险者实例
  - 模板到实例的最小映射关系
- 明确实例最小字段集
- 明确固定叙事角色与普通冒险者的最小身份边界
- 明确人物“显现 / 留存 / 流失 / 回补”的设计入口
- 明确哪些未来字段现在不做，后续通过迁移补值
- 让当前固定冒险者能够被视为第一批实例

## 明确不做

- 大规模随机池刷新
- 完整随机姓名 / 外观 / 稀有度系统
- 冒险者成长曲线
- 好感 / 关系深化
- 阵营 / 黑化 / 对立系统
- 市场 / 招募经济系统
- 全量人物生态平衡调参

## 关键规则

- 当前优先解决“实例边界”，不是“内容量”
- 模板数据继续属于配置层，不直接成为存档主体
- 存档里优先保存实例当前正式状态，而不是生成过程回放
- 生成过程细节可以不保留，但实例不能成为完全无来历黑盒
- 人物不是“预先全部存在，等玩家去点开”
  - 玩家只需要对自己已经接触到的人物负责
  - 未进入玩家视野的人物，不要求先作为完整长期实例存在
- 但人物一旦进入玩家视野，就必须成为稳定实例并进入长期保存
- 随机生成不应表现为“抢任务瞬间系统临时捏一个完美人选”
  - 更合理的是世界状态影响“谁更可能进入玩家视野”
- 人数控制不做硬上限
  - 当前只承认“舒适人物区间”概念
  - 该区间是玩法产物，不是世界常数
  - 它会随着版本内容、岗位需求、可运营深度而变化
- 人物生态必须允许流失
  - 冒险者不应默认永远成功、永远安全、永远留在镇上
  - 后续人物失败、意外、离开、隐退都应成为正式系统空间
- 对旧版本里未明确承诺为长期强后果的内容：
  - 可以迁移为倾向
  - 不应直接迁移为强惩罚或强敌对结果
- 新系统上线后的旧档兼容，应优先靠版本迁移和保护性默认值
  - 不默认翻旧账

## 实例最小字段集（当前意向）

- `instanceId`
  - 稳定实例标识，进入存档后不再变化
- `templateId`
  - 轻量来源锚点
- `originType`
  - 当前至少区分：
  - `handcrafted`
  - `generated`
- `roleType`
  - 当前至少区分：
  - `anchor`
  - `adventurer`
- 当前正式展示与玩法状态：
  - 名称
  - 称号
  - 偏好
  - 人格
  - 正式能力
  - 印象 / 传闻 / 动机等当前已参与展示的字段
  - 已知度与接触状态
  - 当前任务状态
  - 长期关系相关运行时状态
- 当前判断：
  - 不要求保存完整生成扰动明细
  - 不要求保存“为什么长成这样”的过程历史
  - 但保留最少来源锚点，避免后续完全失去兼容抓手

## 当前不预埋的未来字段

- 阵营
- 黑化路线正式状态
- 忠诚 / 背叛正式状态
- 完整成长履历
- 不可逆事件链完整历史

这些字段当前不提前硬塞。

后续如果真的落地，应优先通过：

- 新版本迁移默认值
- 旧记录转倾向而不是直接定案
- 新系统首次接入时再正式确认

来处理旧档兼容。

## 人物显现与流动（本版结论）

### 当前已确认的设计原则

- 新人物的出现应由世界事件、任务结构和玩家当前状态共同影响
- “认识到谁”本身就是玩法的一部分
- 新人物显现要和世界状态挂钩，而不是按死板时间表机械刷新
- 任务和世界状态可以影响人物显现的方向性
  - 例如更容易显现调查型、补货型、高危型人物
  - 但不应直接变成“为了这一单任务临时生成必胜人选”

### 当前已确认的显现窗口方向

- 新一天开始时
- 某类任务完成后
- 地区 / 主题推进后
- 传闻 / 线索扩散后
- 当前人手结构出现明显缺口时

## 任务承接公式边界调整（本版结论）

### 为什么要动旧公式

`v0.10` 已完成的接任务公式，原本解决的是：

- 在“已经进入候选范围的人”里
- 谁更愿意考虑这份任务
- 考虑后谁更可能真的把任务接走

这套逻辑本身没有失效。

但 `v0.13` 新增了一个上层语义：

- 玩家并不会一开始就认识所有冒险者
- 有些任务本身会把陌生人带进玩家视野
- “谁接任务”不再只是已知名册内部竞争

因此旧公式不再足够覆盖完整问题。

### 这次改的是哪一层

这次改的不是人格 / 能力 / 偏好对接任务的正式评分本体。

这次改的是它上面新增的一层：

- 这份任务今天有没有人接
- 如果有人接，是熟人接，还是陌生人接
- 如果是陌生人接，这次承接本身是否构成一次接触事件

换句话说：

- `v0.10` 继续负责“给定候选人后，谁更愿意接”
- `v0.13` 新增负责“这次候选渠道来自哪里”

### 这次明确不改什么

- 不重做人格在接任务中的主场分工
- 不重做能力在接任务中的主场分工
- 不推翻公共任务 / 筛选任务的区分
- 不重写连续曲线和边界重叠原则
- 不把原有候选人评分逻辑改成全新系统

### 这次新增后的正式问题结构

任务承接现在应被理解成三层问题：

1. 这份任务今天是否会被接
2. 如果会被接，是由熟人接，还是由陌生人接
3. 在该渠道内，具体由谁接

当前判断：

- 第 3 层继续复用 `v0.10` 逻辑
- 第 1 层和第 2 层由 `v0.13` 新增的上层分流来解决

### 后续版本如果继续动老公式，建议沿用同样写法

每次调整旧公式时，至少写清：

- 为什么要改
- 改的是哪一层
- 明确不改什么
- 新版本新增了什么语义，导致旧问题边界变化

这样后面即使继续叠版本，也不会把“旧公式失效”和“新系统上层分流”混写在一起。

### 当前已确认的人数原则

- 不做硬人数上限
- 做“舒适人物区间”的软抑制
- 人越多，新人物显现概率可以递减
- 但概率不应直接归零
- 特殊事件、地区推进、强结果回流可以突破常态

### 当前已确认的流失方向

- 人物后续必须允许流失
- 流失不一定只等于死亡
- 也可以包括：
  - 离开镇子
  - 长期不再出现
  - 转去其他地区
  - 多次失败后的隐退
  - 事故导致的阶段性退出

## 本版要解决什么

- 模板 / 实例 / 固定叙事角色 / 普通冒险者的正式结构边界
- 实例创建入口
- 实例稳定标识
- 为后续“显现时才生成实例”留出结构位置
- 把“人物显现与流动”从想法变成正式设计原则

## 本版不要求完整落地什么

- 不要求真正实现完整人物显现机制
- 不要求真正实现人数软抑制公式
- 不要求真正实现失败 / 离开 / 流失事件
- 不要求真正实现地区推进驱动的人物池变化
- 不要求真正实现基于任务结构的生成偏向算法

这部分本版先立设计入口和结构边界，不在这一版把所有动态生态一次做完。

## 旧固定冒险者并入策略

- 当前 `config/adventurers.json` 里的固定人物，先视为模板来源
- 本版不急着做完整模板库重构
- 先允许它们作为“首批已生成实例”进入运行时
- 旧档读入时：
  - 不要求回放生成过程
  - 只要求能稳定恢复当前实例状态

## 验收标准

- 代码中已能正式区分模板和实例
- 当前固定冒险者不再只能以“模板即实例”的方式存在
- 冒险者实例已有稳定 id 和最小来源锚点
- 新版本继续做随机生成或养成时，不需要再推翻实例骨架

## 风险和待定问题

- 如果模板和实例继续混写，随机系统一进来就会带着存档和成长一起返工
- 如果实例完全不留来源锚点，后续新系统迁移只能靠猜
- 如果现在就预埋太多未来字段，又会把还没定义清楚的系统硬塞进存档骨架

## 跨版本待处理

- 随机冒险者生成
- 实例池刷新规则
- 冒险者成长
- 阵营 / 黑化等强后果系统
- 旧档接入这些新系统时的定向迁移

## 结果记录

- 版本开始时先确认：
  - 下一步不直接做完整随机生成
  - 也不先做完整养成
  - 当前真正的前置工作，是把“长期人物实例”正式立起来
- 当前已确认的设计判断：
  - 玩家更在意“这个人现在是谁”，而不是“当初生成时每一步怎么算”
  - 因此存档应优先保存实例当前正式状态
  - 但完全抹掉来源信息并不稳，至少要保留少量来源锚点
  - 旧版本里只服务文本差异、未明确承诺长期强后果的选择，后续不应被直接追溯成重惩罚
  - 玩家不需要对“所有可能存在的人”负责，只需要对自己已经接触到的人负责
  - 因此后续更合理的方向是：人物先显现，再作为正式实例进入长期存档
  - 舒适人物区间是玩法阶段和岗位需求共同决定的动态结果，不应写死成常量
  - 当前判断：`v0.13` 已经从“小骨架版”升级为“工作量较大的中间版本”
  - 因此这版允许多停留，优先把人物实例和人物显现入口做完整，少留坑
