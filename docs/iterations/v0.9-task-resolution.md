# v0.9 Task Resolution

> 后续状态：本版当时使用的技术矩阵和模拟脚本已在 `v0.13` 内容重构后正式退役。结算公式本体仍保留在 `src/game/systems/quests/taskResolution.ts`；本文中的脚本命令仅作为历史开发记录，不再是当前项目命令。

## 本次目标

为任务建立第一版正式结算骨架，让“任务会发生什么”不再主要依赖测试控制字段，而开始具备可扩展的成功 / 失败判断入口。

这版重点不是把完整战斗、伤病、死亡、地图都做完，而是先把后续所有这些系统共同依赖的结算入口搭起来。

## 本次范围

- 明确任务结算阶段的最小输入
- 明确线索在结算中的第一版作用
- 明确结算结果的最小输出
- 先决定后续要吃哪些人物能力输入，但暂不把完整属性系统一次铺满
- 为后续失败回传、部分成功、伤病、死亡、组队等内容预留位置

## v0.9 必须解决

这版不是继续无限补“临时能跑”的方案，而是要把当前已经暴露的问题收成长期可保留结构。

本版必须解决的核心是：

- 任务结算的正式输入结构
  - 任务隐藏特征不能继续只停留在粗粒度字段上
- 冒险者能力的第一版正式骨架
  - 不再继续依赖明显临时的能力集合
- 人格层与能力层的分工
  - 避免后续成长、结算、接任务逻辑反复返工
- 参数量纲与区间约定
  - 哪些值是原始属性
  - 哪些值是公式标准化后的有效值
  - 哪些值当前只需要统一量纲
  - 哪些值未来才值得做软上限或预算控制
- 模拟脚本与正式结算共享同一套正式逻辑
  - 不允许脚本和正式代码长期各维护一套

如果这几项不收稳，后续的成长、失败后果、线索深化都会继续建立在临时结构上，返工成本会越来越高。

## 明确不做

- 完整战斗系统
- 完整属性面板
- 完整伤病 / 死亡 / 墓地系统
- 组队系统
- 地图系统
- 把所有底层属性直接展示给玩家

## 关键规则

- 先做“任务如何结算”，再做“人物有哪些正式能力值”
- 冒险者能力后续应尽量服务于统一底层属性，而不是分裂成多套彼此孤立的属性表
- 玩家可见信息应少于系统内部用于计算的属性与参数
- 线索的第一价值是降低未知、改善判断；第二价值才是逐步影响成功率、失败率、稳定性等结果参数
- 当前版本优先建立可维护的结算骨架，不追求一次把公式做得很复杂
- 允许失败，但应尽量避免“玩家已做足准备，仍被固定底噪概率硬判重大坏结果”的烦躁体验
- 后续重大坏结果更应建立在高风险、准备不足、人员不匹配或连续错误决策上，而不是小额保底霉运
- 测试专用项只应用于绕过大量前置、直接验证当前模块；不应为了“以后也许会用”提前增加额外模式

## 第一版结算最小输入

- 任务基础风险
- 任务基础难度
- 任务性质
- 任务耗时
- 线索修正
- 冒险者能力修正
- 人格带来的意愿与风格差异

## 第一版结算最小输出

- 成功
- 失败
- 结果摘要
- 线索 / 发现 / 资源 / 后续状态变化

## 属性方向约定

这版不单独做“完整属性系统”主题，但会先明确后续属性设计原则：

- 内部属性可以相对丰富
- 玩家可见信息必须经过压缩和转译
- 不追求把所有参与公式的属性都直接展示给玩家
- 后续更适合采用“统一底层属性 + 不同结算场景各取所需”的方式，而不是为战斗、冒险、调查分别发明完全独立的属性体系
- 后续正式扩属性时，每个属性都应至少有一个高权重主场公式；如果没有主场，就只能作为少量通用修正项存在
- 不应长期保留“没有主场、也没有明确全局用途”的重复属性

## 验收标准

- 任务结算不再只能依赖 `testOutcomeMode`
- 文档中明确第一版结算输入与输出
- 线索对结算的作用不再只停留在“解锁任务”
- 后续能力系统的入口已经足够清楚，继续开发时不会先做一堆孤立属性

## 风险和待定问题

- 如果过早把公式做太重，调试和验证都会迅速变难
- 如果属性定义过多但暂时没有真正用到，会形成新的空转数据层
- 如果结算结果仍然过于单薄，后续人物成长和任务后果依然会显得不够真实
- 如果随机性主要体现在“无理由翻车”，会直接伤害培养冒险者这条核心体验

## 跨版本待处理

- 后续需要把线索数量、线索质量、线索来源逐步接入结算修正
- 后续可扩展到部分成功、伤病、失联、死亡、残缺回报
- 后续需要把任务结算与消息回传方式更紧密地接在一起
- 后续需要让任务认知层与正式结算参数形成稳定映射，而不是长期只靠少量标签支撑

## 明确转入 v0.11 的遗留项

以下内容不是不重要，而是应该建立在 `v0.9` 结构稳定之后再做：

- 结果可解释性增强
  - 让玩家更容易看懂“为什么成功 / 为什么失败”
- 部分成功 / 部分失败
  - 不再只保留最小二元结果
- 伤病、长期代价、后续恢复
- 线索质量和线索来源更复杂地进入公式
- 更成熟的测试矩阵与内容校验工具
- 把当前新的结算结构更完整地映射到 UI 解释层

这些更适合作为 `v0.11` 的主目标，而不是继续和 `v0.9` 的核心结构整理混在一起。

## 明确后置，不进入 1.0 当前主线

以下内容当前应继续保持后置：

- 组队系统
- 冒险者之间关系
- 自由贸易市场
- 冒险者自主经济循环
- 完整地图系统
- 墓地 / 老去 / 长期命运完整闭环
- 圣堂 / 地下交易

这些不是无用，而是当前还没有足够稳定的前置骨架，不应抢占 `1.0` 主线开发资源。

## 当前收口判断

按当前版本边界，`v0.9` 现在应进入“收口”而不是继续扩主题。

### 当前版本内可以接受的完成状态

- 任务结算正式逻辑已不再依赖 `testOutcomeMode`
- 任务隐藏特征、正式能力、人格修正、线索修正都已接入同一套正式结算
- 标准任务基准已命中
- 五项正式能力都已有可验证主场
- 当前公式虽然仍然简化，但已足够承担 `v0.9` 的“长期保留骨架”职责

### 当前版本只剩的最小收尾项

- 保持当前结算参数作为本版暂定冻结值
- 保持模拟脚本默认最小验证输出，不再继续膨胀测试模式
- 如后续需要，只补少量结论性记录，不再继续扩展本版设计范围

### 明确不再继续塞入 `v0.9`

- 接任务公式正式重构或深调
- 随机冒险者 / 随机任务系统
- 好感 / 关系深化
- 冒险过程中的中间事件层
- 市场系统

这些内容都属于后续阶段，不应继续混入当前结算版本。
