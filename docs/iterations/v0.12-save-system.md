# v0.12 Save System

## 本次目标

在 `v0.11` 的结果层 / 解释层骨架稳定后，补项目的正式存档骨架。

这版要解决的不是：

- 做新的玩法内容
- 做随机冒险者
- 做随机任务

这版要解决的是：

- 当前 `GameData` 如何被正式保存和恢复
- 哪些数据必须进入存档，哪些不应直接落盘
- 存档版本升级时，后续如何迁移而不是直接报废旧档

换句话说：

- `v0.11` 解决“结果如何正式表达”
- `v0.12` 解决“这些状态如何正式保存”

## 本次范围

- 正式定义存档数据入口
- 正式定义：
  - 存档格式版本号
  - 导出 / 导入边界
  - 本地持久化边界
- 明确 `GameData` 中哪些字段应直接保存，哪些应在读档时重建
- 补最小可用的本地存档读写方案

## 明确不做

- 云存档
- 账号系统
- 多存档槽位的完整交互设计
- 随机冒险者
- 随机任务
- 市场
- 更复杂的回放 / 历史追踪系统

## 关键规则

- 存档系统属于基础设施，不应和新玩法开发混在同一版里
- 存档格式必须带版本号
- 当前存档优先服务开发期：
  - 稳定保存
  - 稳定恢复
  - 版本升级可迁移
- 存档应优先保存“状态事实”，而不是保存大量可由代码即时重建的显示文本
- 内部结构变化后，不应默认旧档全部失效
  - 至少应预留迁移入口
- 当前环境优先考虑：
  - 浏览器本地存储
  - 文本导出 / 导入
- 不应把临时测试数据和正式运行存档混写成一套模糊结构

## 验收标准

- 当前运行状态可以稳定保存与恢复
- 存档结构有明确版本号
- 主要状态数据不会因页面刷新直接丢失
- 后续版本新增字段时，已有明确迁移入口

## 风险和待定问题

- 如果现在不先做版本化，后续随机人物和结果层变复杂后会很难兼容旧档
- 如果直接把整个 `GameData` 原样序列化，后续重构成本会很高
- 如果存档边界不清，测试状态和正式状态会互相污染
- 如果过早做复杂存档 UI，会再次挤占玩法主线

## 跨版本待处理

- 多存档槽位
- 云同步
- 更复杂的导入 / 导出体验
- 随机冒险者与随机任务接入后的旧档迁移
- 更精细的开发期调试存档

## 结果记录

- 版本开始时先记录范围
- 当前立项理由：
  - `QuestResult`、接任务状态、消息板记录已经开始变得值得长期保留
  - 再往后接随机人物 / 随机任务，如果没有正式存档，回归和验证成本会明显上升
- 当前已知需纳入存档边界的新增点：
  - 玩家的 `resultInsightLevel`
  - 这条能力后续不应孤立存在，应优先挂到据点设施 / 固定资产 / 势力能力线中的某一条
- 当前已确认的落地边界：
  - 存档不直接序列化整个 `GameData`
  - 配置型数据继续从代码与配置文件重建：
    - `resources`
    - `questTemplates`
    - `intelDefinitions`
    - 冒险者静态模板信息
  - 运行期事实进入存档：
    - 日期、金钱、任务列表、库存、消息板记录、日志、冒险者运行时状态、置顶状态
  - `QuestResult` 进入存档时只保留事实字段：
    - `type / outcome`
    - `resourceId / quantity`
    - `intelKind / intelId`
    - `matchingIntelCount`
    - `successChance / rolledChance`
    - `reasonTags`
  - 以下字段不直接落盘，统一在读档时重建：
    - `QuestResult.summary`
    - `details.visibleReasonTags`
    - `details.display`
  - 当前判断：
    - `resultInsightLevel` 属于玩家长期状态，应直接保存
    - `visibleReasonTags` 只是正式原因标签的可见切片，不应单独保存
    - `details.display` 属于展示覆写层，不应成为长期事实
    - `QuestResult.summary` 继续保留为运行期兼容字段，但不作为存档核心
