# 迭代文档规范

这个目录用于存放每一个小版本对应的迭代文档。

## 目的

迭代文档要和代码版本绑定，用来回答下面几个问题：

- 这个版本想解决什么问题
- 这次只做哪些内容
- 哪些内容明确不做
- 哪些规则是暂定的
- 做完以后还遗留了什么问题

## 建议流程

1. 开始一个明确的小版本前，新建分支。
2. 在这个目录下新建一份迭代文档。
3. 先写清楚目标、范围和边界，再开始改代码。
4. 开发中如果设计发生变化，及时补到文档里。
5. 版本完成后，把结果、遗留问题和下一步建议补齐。

## 分支命名建议

- `feat/mvp-day-loop`
- `feat/adventurer-system`
- `feat/quest-resolution`
- `docs/design-cleanup`

分支名最好体现这次迭代的主题，而不是随手起一个泛泛的名字。

## 文件命名建议

推荐格式：

- `v0.1-day-loop.md`
- `v0.2-adventurer-core.md`
- `v0.3-quest-and-return.md`

如果后面需要，也可以在文件名前加日期，但版本主题仍然应该保留。

## 每份文档至少包含的内容

### 1. 本次目标

这次迭代最想验证或完成的内容是什么。

### 2. 本次范围

这次明确会做什么。

### 3. 明确不做

这次故意不碰什么，防止范围不断膨胀。

### 4. 关键规则

这次版本依赖的核心规则，例如时间推进方式、任务结算方式、数据结构假设等。

### 5. 验收标准

做到什么程度，算这个版本可用。

### 6. 风险和待定问题

当前还没想清楚，或者实现中可能出问题的地方。

### 7. 结果记录

版本做完后再补，记录实际完成情况和与原计划的偏差。

## 与私人备忘的区别

`docs/notes/` 里的内容偏长期想法、灵感和方向判断，可以不进 Git。

`docs/iterations/` 里的内容偏版本记录和工程决策，建议进 Git，这样回溯某个版本时，代码和当时的设计说明能一起看。
