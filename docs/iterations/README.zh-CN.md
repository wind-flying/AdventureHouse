# 迭代文档规范

这个目录用于存放每一个小版本对应的迭代文档。

## 目的

迭代文档要和代码版本绑定，用来回答下面几个问题：

- 这个版本想解决什么问题
- 这次只做哪些内容
- 哪些内容明确不做
- 哪些规则是暂定的
- 做完以后还遗留了什么问题

如果某个版本引入了测试专用字段、测试标签、原型命名或临时行为控制项，还应同步更新：

- [testing-artifacts.zh-CN.md](/home/windflying/Code/AdventureHouse/docs/iterations/testing-artifacts.zh-CN.md)

如果某项功能已经进入“以后靠配置文件长期扩内容”的阶段，还应优先补一份对应的编写指南，避免后续新增内容时又回到“必须翻代码才能写配置”的状态。

如果某个系统已经开始依赖较多公式、调参项或权重关系，也应优先补一份说明文档，至少写清：

- 哪些结果会受哪些输入影响
- 当前影响方向是增加、减少还是分段处理
- 哪些值带上下界、上限或截断

这样后续调参时就不需要每次都重新翻逻辑代码。

如果某个系统同时存在：

- 已经支持的正式写法
- 以及已经讨论过、但尚未实装的后续规划

那么文档里应明确区分“当前已实现”和“后续规划”，避免把两者混写成一份模糊说明。

如果某项内容后续主要依赖人工编辑配置文件扩展，还应及时记录是否需要配套的校验工具，避免内容文件越来越多后只能靠人工肉眼排查。

这样后续清理测试遗留时，能明确知道项目里到底引入过哪些“只为验证而存在”的东西。

## 建议流程

1. 开始一个明确的小版本前，新建分支。
2. 在这个目录下新建一份迭代文档。
3. 先写清楚目标、范围和边界，再开始改代码。
4. 开发中如果设计发生变化，及时补到文档里。
5. 版本完成后，把结果、遗留问题和下一步建议补齐。
6. 如果准备开始一个新功能，先对照相关文档，确认之前讨论过的设计是否已经落档，再开始写代码。

## 分支命名建议

- `feat/mvp-day-loop`
- `feat/adventurer-system`
- `feat/quest-resolution`
- `docs/design-cleanup`

分支名最好体现这次迭代的主题，而不是随手起一个泛泛的名字。

## 文件命名建议

推荐格式：

- `v0.1-day-loop.md`
- `v0.2-adventurer-core.md`
- `v0.3-quest-and-return.md`

如果后面需要，也可以在文件名前加日期，但版本主题仍然应该保留。

## 每份文档至少包含的内容

### 1. 本次目标

这次迭代最想验证或完成的内容是什么。

### 2. 本次范围

这次明确会做什么。

### 3. 明确不做

这次故意不碰什么，防止范围不断膨胀。

### 4. 关键规则

这次版本依赖的核心规则，例如时间推进方式、任务结算方式、数据结构假设等。

### 5. 验收标准

做到什么程度，算这个版本可用。

### 6. 风险和待定问题

当前还没想清楚，或者实现中可能出问题的地方。

### 7. 跨版本待处理

这部分用于记录已经发现、但不要求在下一个版本立刻解决的问题。

它的含义是：

- 这些问题已经被注意到
- 后续窗口或后续版本需要能看到它们
- 但它们不是“上一版没做完，所以紧接着下一版必须完成”的事项

### 8. 结果记录

版本做完后再补，记录实际完成情况和与原计划的偏差。

## 编码结构约定

后续迭代默认遵守下面这条原则：

- 新增功能时，优先判断能否拆成新文件，而不是继续把旧文件越堆越大
- 旧文件更适合保留“编排”和“入口”职责，新完成的规则或显示细节应尽量拆到独立模块
- 内部标识和展示内容要分离，例如资源 id、状态值、任务内部 id 不应直接暴露给玩家界面
- 业务逻辑不要顺手拼显示文本，文本模板和显示映射应尽量集中管理
- 配置数据、运行逻辑、显示文本、界面渲染应尽量分层，不要混写在同一个文件里
- 暂时用于平衡或验证玩法的调参值，不应散落在逻辑中，至少要集中放在文件顶部或独立调参区，并给出能看懂用途的名字

当前可以按下面的思路理解：

- `config/`：静态配置，例如资源、任务模板、冒险者基础资料
- `text/`：故事文本、反馈文案、状态描述
- 规则模块：时间推进、任务推进、结算规则
- UI 模块：只负责把可显示数据渲染出来

这是一条长期约定，不要求一次性把所有历史代码都重构完，但后续新增代码默认按这条标准执行。

## 与私人备忘的区别

`docs/notes/` 里的内容偏长期想法、灵感和方向判断，可以不进 Git。

`docs/iterations/` 里的内容偏版本记录和工程决策，建议进 Git，这样回溯某个版本时，代码和当时的设计说明能一起看。
