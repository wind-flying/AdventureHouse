# 任务结算与接取公式说明

## 文档用途

这份文档专门说明当前版本里：

- 谁会去接任务
- 调查 / 异常任务如何判定成功或失败

会受到哪些因素影响，以及这些影响大致是什么方向。

目标不是让你背代码，而是让你在后续调参时能快速判断：

- 哪个因素目前有没有被用到
- 是线性增加还是线性减少
- 是固定加减、分段处理，还是带上限 / 下限

## 这份文档和模拟脚本怎么配合

从 `v0.9` 开始，任务结算进入“公式验证”阶段。

这不等于界面不重要了，而是意味着：

- 界面层当前优先保证“显示正确、结果可看懂”
- 公式、权重、能力影响、线索修正这类问题，更适合先用模拟脚本快速验证
- 等脚本确认方向后，再决定要不要继续改 UI 呈现和内容样例

也就是说，后续这一阶段会更频繁地和测试脚本打交道，但不是在做传统意义上的“后端开发”；更准确地说，是在做`系统规则验证`。

## 当前结论先看

当前有两套相邻但不同的公式：

1. `任务接取公式`
   - 决定谁愿意接任务
   - 主要吃人格、风险、性质、报酬、时长、最近是否刚做过任务

2. `任务结算公式`
   - 决定调查 / 异常任务最后成功还是失败
   - 主要吃风险、难度、时长、线索数量、冒险者能力、少量人格修正

补货 / 日常任务当前还没有进入正式结算公式，暂时默认稳定成功。

## 当前基准设定

当前 `v0.9` 先采用一套内部基准，用来配平公式，而不是直接视为玩家可见设定：

- 冒险者能力原始值基准：`35`
- 标准任务：
  - 指的是普通随机刷出的、没有特别极端特征的调查任务
- 标准任务目标概率：
  - 优势人选：`60% ± 3%`
  - 劣势人选：`45% ± 3%`

这里的意思不是“所有标准任务都固定等于这两个值”，而是：

- 当任务处于标准区间
- 且人物能力只是在平均值附近上下浮动
- 那么优势者和劣势者在成功率上应大致落在这两个体验区间

后续如果基准要改，也应该先改这组目标，再反推公式，而不是只改单个权重。

当前 `resolution` 主题中的任务和角色命名，也已经改成纯技术命名，例如：

- `resolution / standard / advantage`
- `resolution / exploration / strong`
- `resolution / combat / weak`

目的不是做世界观内容，而是让你在看模拟和对照时，能直接把样例对应回：

- 哪项能力是主场
- 哪条任务在测哪组隐藏特征
- 当前结果到底是在验证基准、主场差异，还是线索修正

## 当前 v0.9 的第一批正式输入

当前 `v0.9` 已开始把任务结算从“公开粗字段”逐步切到“公开字段 + 隐藏特征”的组合。

### 任务侧

公开字段仍保留：

- `risk`
- `difficulty`
- `timingMode / fixedDurationDays`

这些字段目前主要继续服务于：

- 玩家可见信息
- 基础文案
- 旧内容兼容

同时新增一层隐藏特征：

- `danger`
- `challenge`
- `durationPressure`
- `uncertainty`
- `investigationComplexity`
- `reportDifficulty`
- `stability`

这组输入主要服务于正式结算公式和模拟脚本。

当前建议的长期写法是：

- 配置里的任务隐藏特征：优先写 `0 ~ 100` 的原始值
- 公式内部：再统一标准化成 `0 ~ 1` 的有效值

兼容说明：

- 旧测试内容如果仍写 `0 ~ 1`
- 当前代码会自动兼容并转成正式量纲
- 但后续新内容建议尽量直接写 `0 ~ 100`

### 冒险者侧

第一批正式能力当前收成 5 项：

- `physique`
- `survival`
- `exploration`
- `observation`
- `combat`

人格层仍保留，用于：

- 接取意愿
- 主观风险判断
- 对自己能力的主观评估偏差

当前建议的长期写法是：

- 配置里的能力值：作为原始属性值，可继续成长，不必硬锁死在 `0 ~ 1`
- 公式内部：再把原始值映射成 `0 ~ 1` 的有效值
- 当前阶段的重点是先把“原始值”和“公式有效值”分开，并统一量纲；不应为了以后可能会用，就提前把软上限全局接进所有能力计算

## 一、任务接取公式

### 作用

当前接取逻辑分两步：

1. 先算“这个人愿不愿意考虑这份任务”
2. 再在愿意接的人里排序和随机挑选

### 1. 接取分数

接取分数当前受下面这些影响：

- 资源偏好
  - 只对仍然保留 `resource` 的任务生效
  - 固定正向加成
  - 影响方式：固定加法

- 勤勉
  - 对 `routine / supply` 更强
  - 对其他任务也有轻微正向影响
  - 影响方式：线性乘法后加到总分

- 勇气
  - 高危任务：强正向
  - 有风险任务：中等正向
  - 安全任务：轻微负向
  - 影响方式：按风险分段，再做线性乘法

- 逐利
  - 看的是 `reward / totalDays`
  - 先按基准线归一化，再线性加减
  - 影响方式：线性，但先做了截断归一化

- 社交
  - 轻微通用加成
  - 影响方式：线性加法

- 审慎
  - 安全任务：正向
  - 中风险：负向
  - 高危：强负向
  - 影响方式：按风险分段，再做线性乘法

- 求知
  - 异常任务：强正向
  - 调查任务：中等正向
  - 日常 / 补货：只保留很轻的影响
  - 影响方式：按性质分段，再做线性乘法

- 纪律
  - 短任务：正向更强
  - 长任务：仍有轻微正向
  - 影响方式：按时长分段，再做线性乘法

- 韧性
  - 长任务：正向更强
  - 短任务：轻微正向
  - 影响方式：按时长分段，再做线性乘法

- 随机扰动
  - 当前会加一个小随机数
  - 影响方式：随机正向扰动

### 2. 接取阈值

不是所有空闲冒险者都会参与排序。

当前每个人还会有一个“愿意考虑任务”的阈值，受这些因素影响：

- 基础阈值
  - 固定起点

- 勤勉
  - 越高，阈值越低
  - 更容易考虑任务
  - 影响方式：线性降低

- 逐利
  - 越高，阈值越低
  - 更容易被任务打动
  - 影响方式：线性降低

- 审慎
  - 越高，阈值越高
  - 更容易观望
  - 影响方式：线性升高

- 社交
  - 越高，阈值越低
  - 更容易参与公共事务
  - 影响方式：线性降低

- 纪律
  - 越高，阈值越低
  - 更容易保持合作节奏
  - 影响方式：线性降低

- 最近是否刚做完任务
  - 当天刚结束：阈值明显升高
  - 前一天刚结束：仍然升高
  - 闲置数天后：阈值下降
  - 影响方式：固定加减

### 3. 当前性质总结

接取公式现在主要是：

- 固定加减
- 分段线性
- 小随机扰动

当前还没有：

- 反比例
- 指数增长
- 对数衰减

## 二、任务结算公式

### 当前适用范围

当前正式结算只作用于：

- `publishMode = "intel"` 的调查 / 异常任务

补货 / 日常任务当前仍直接成功，不进入这套成功率计算。

### 当前结果结构

目前结果还是二元：

- 成功
- 失败

还没有：

- 部分成功
- 伤病
- 失联
- 死亡

### 当前覆盖关系

先看这一条最重要：

- 如果模板写了 `testOutcomeMode = "success"` 或 `"failure"`
  - 会直接强制结果
  - 这是最高优先级

- 只有在没有强制结果时
  - 才走正式成功率计算

### 成功率当前怎么计算

当前调查任务的成功率，基本可以理解成：

`基础成功率`
`- 危险性惩罚`
`- 难度惩罚`
`- 耗时压力惩罚`
`- 未知度惩罚`
`- 回传难度惩罚`
`+ 稳定性修正`
`+ 线索修正`
`+ 能力修正`
`+ 少量人格修正`

最后再做上下界截断。

## 当前量纲约定

为了减少“参数很多，但不知道谁该重谁该轻”的问题，当前开始明确区分：

- 原始值
- 有效值

### 1. 任务隐藏特征

- 原始值：建议 `0 ~ 100`
- 有效值：统一标准化成 `0 ~ 1`

### 2. 冒险者正式能力

- 原始值：开放增长，不要求硬上限
- 有效值：进入公式时映射到 `0 ~ 1`

### 3. 人格

- 当前仍使用 `-1 ~ 1`
- 暂时继续作为较直接的修正输入

### 4. 基准值与标准任务

- 当前内部基准能力值：`35`
- 这不是世界观里的公开规则，而是公式配平基准
- 当前新增了两条专门的标准任务样例：
  - `resolution-standard-advantage`
  - `resolution-standard-challenge`
- 它们用于检验：
  - 优势人选是否接近 `60% ± 3%`
  - 劣势人选是否接近 `45% ± 3%`

## 软上限约定

当前不建议把“属性本体”直接做成固定硬上限。

更合理的方向是：

- 原始属性值继续增长
- 进入公式后再转成有效值
- 当且仅当后续真的需要控制玩家可长期追求的属性收益时，才在临界区让有效值增长逐步放缓

这意味着：

- 玩家或内容配置依然能继续提升属性
- 但后续如果真的接入成长型软上限，同一项能力不会无限线性放大结果
- 线索、任务特征、人格修正等其他输入仍然保有存在感

当前阶段先明确这几个原则：

- 软上限只适合优先用于“玩家可长期追求、可持续培养、可不断堆叠”的属性
- 不应提前全局套在所有输入上，尤其不应直接套在任务危险度、难度、未知度这类任务侧输入上
- 软上限应主要在临界区生效：
  - 临界区之前，提升应尽量保持近似线性
  - 只有接近临界区时，边际收益才开始明显递减
- `v0.9` 当前主目标仍是先把：
  - 原始值
  - 公式有效值
  - 统一量纲
  收稳，而不是提前把成长型软上限全面铺开

### 1. 基础成功率

- 固定起点：`0.7`
- 含义：什么都不修正时，调查任务默认偏向“有机会做成”，但后续会被惩罚项明显往下拉
- 影响方式：固定常量

### 2. 总惩罚预算

- 当前不再让每个负项各自无限往下压，而是先设一块总惩罚预算
- 当前总惩罚预算：`0.42`
- 然后再把这块预算分配给：
  - 危险性
  - 难度
  - 耗时压力
  - 未知度
  - 回传难度

含义：

- 这样可以更清楚地知道：
  - 现在到底是某一项太重
  - 还是总预算本身过大
- 也能避免“每一项单独看都不夸张，但总和一叠就过低”的问题

影响方式：

- 分预算后线性递减

### 3. 危险性惩罚

- 主要看隐藏特征里的 `danger`
- 值越高，惩罚越重
- 当前分到的惩罚预算占比：`28%`

含义：

- 这件事本身有多危险
- 更偏“出事有多严重、外部压力有多大”

影响方式：

- 线性递减，但受总惩罚预算约束

### 4. 难度惩罚

- 主要看隐藏特征里的 `challenge`
- 值越高，惩罚越重
- 当前分到的惩罚预算占比：`24%`

含义：

- 这件事有多难做好
- 更偏“对能力和判断的要求有多高”

影响方式：

- 线性递减，但受总惩罚预算约束

### 5. 耗时压力惩罚

- 主要看隐藏特征里的 `durationPressure`
- 值越高，惩罚越重
- 当前分到的惩罚预算占比：`15%`

含义：

- 这条任务在时间维度上有多拖人
- 更偏“持续消耗和长线压力”

影响方式：

- 线性递减，但受总惩罚预算约束

### 6. 未知度惩罚

- 主要看隐藏特征里的 `uncertainty`
- 值越高，惩罚越重
- 当前分到的惩罚预算占比：`19%`

含义：

- 玩家和冒险者当前对任务有多不了解
- 线索的第一价值主要就是压低这项

影响方式：

- 线性递减，但受总惩罚预算约束

### 7. 回传难度惩罚

- 主要看隐藏特征里的 `reportDifficulty`
- 值越高，惩罚越重
- 当前分到的惩罚预算占比：`14%`

含义：

- 即使做成了，也有多难把完整信息带回来
- 现在先轻度进入成功率，后续更适合继续影响结果质量和消息完整度

影响方式：

- 线性递减，但受总惩罚预算约束

### 8. 稳定性修正

- 主要看隐藏特征里的 `stability`
- 值越高，加成越明显

含义：

- 这条任务是不是容易“按预期推进”
- 用来区分：
  - 危险但明确
  - 混乱难控

影响方式：

- 线性修正

### 9. 线索修正

当前看的是：

- 同一 `lineId` 下
- 玩家已经掌握了多少条不同的线索 / 发现

规则：

- 每条独立线索：`+0.035`
- 最高加成上限：`+0.12`

## 三、批量模拟工具

为了减少反复手动点界面、推进天数、再回头看结果的成本，当前提供了一个专门用于 `v0.9` 的批量模拟脚本：

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution
```

当前项目实际更推荐使用项目内 Node 运行时：

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution
```

如果你是在 Windows 浏览器 / Windows 终端配合 WSL 开发，这条命令通常比直接运行 `npm run ...` 更稳。

### 适合什么时候用

- 你想快速看某条测试任务的成功率拆解
- 你想比较同一条任务在不同线索数量下会怎么变化
- 你想判断当前公式是不是太松、太紧、还是某个因素权重太弱

### 参数说明

#### `--runs`

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --runs 5000
```

作用：

- 指定随机模拟的次数

影响：

- 值越大，经验成功率越接近公式理论值
- 值越小，波动越大，但出结果更快

当前默认值：

- `1000`

建议：

- 日常快速看趋势：`500 ~ 1000`
- 想看更稳定统计：`3000 ~ 5000`

#### `--intel-count`

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --intel-count 2
```

作用：

- 临时指定“同主题已掌握线索数量”

影响：

- 不会改实际存档
- 只是把这条数字直接带进正式结算公式
- 用来观察线索加成是不是过强或过弱

当前默认值：

- `0`

#### `--quest`

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --quest resolution-standard-advantage
```

作用：

- 只输出某条结算测试任务的报告

影响：

- 方便聚焦单个样例，不必每次都看整组矩阵
- 可以重复传入多次，对照多个任务

例如：

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --quest resolution-physique-strong --quest resolution-combat-strong
```

### 当前输出里会看到什么

脚本当前分两层输出：

- 默认模式
  - 只输出 `v0.9` 收口真正需要的最小验证：
    - 标准基准是否命中
    - 五项能力是否各自有主场
    - 上界截断语义是否正确
- `--full`
  - 再输出逐任务完整拆解：
    - 任务标题与 `id`
    - 强制接取者
    - 任务参数摘要
    - 成功率拆解
    - 多轮模拟统计
    - `0 ~ 3` 条线索时的对照结果

### 这一步在开发流程里的意义

如果你发现某条任务“体验上总觉得不对”，当前更推荐先：

1. 跑模拟脚本看拆解
2. 确认是：
   - 风险太轻
   - 线索加成太强
   - 能力差异不明显
   - 还是人格修正几乎没体感
3. 再决定改公式、改任务样例，还是补新的任务隐藏特征

这比纯靠手点界面反复试更快，也更容易定位问题。

含义：

- 线索越多，未知越少，成功率越高
- 但不会无限叠加

影响方式：

- 线性增加
- 带上限

### 10. 能力修正

当前能力修正已不再只看旧的 4 项能力，而是看 5 项正式能力：

- `physique`
- `survival`
- `exploration`
- `observation`
- `combat`

不同任务会根据隐藏特征，动态计算每项能力的权重。

也就是说：

- 不是每条任务都固定“观察最重要”
- 而是看这条任务在：
  - 危险性
  - 未知度
  - 调查复杂度
  - 回传难度
  - 耗时压力
  上分别有多高

当前不是按“任务性质预设一套固定权重”，而是按隐藏特征动态分配，并且已经允许某些任务形成双高主场：

- `physique`
  - 更吃耗时压力
- `survival`
  - 更吃危险性、低稳定性、少量耗时压力
- `exploration`
  - 更吃难度，未知度只保留中等影响
- `observation`
  - 更吃调查复杂度、回传难度，未知度只保留较轻影响
- `combat`
  - 更吃危险性和异常性质

然后会拿这组动态权重做“主需求更重”的聚合，再与中心值 `0.35` 比较：

- 高于 `0.35`：正向修正
- 低于 `0.35`：负向修正

最后乘以权重系数 `1.08`

当前还额外有一条聚合原则：

- 权重不会只线性平均
- 会再经过 `capabilityWeightPower = 2` 的放大
- 目的不是把任务做成单一主属性，而是让真正的高需求项更有体感
- 允许双高，但不允许某项能力长期没有自己的高权重场景

也就是说：

- 能力越高，成功率越高
- 能力越低，成功率越低
- 当前先按统一量纲做线性映射，不在这一步提前全局套软上限

影响方式：

- 先加权平均
- 再围绕中心值做线性增减

### 11. 人格修正

当前只接了少量最贴近结果的修正：

- 求知
  - 调查任务：正向
  - 异常任务：更强正向

- 审慎
  - 高未知：负向
  - 高危险：负向

- 勇气
  - 高危任务：轻微正向

- 韧性
  - 长任务：轻微正向

影响方式：

- 按任务性质或隐藏特征做线性加减

### 12. 上下界截断

当前成功率最后会被限制在：

- 最低：`0.18`
- 最高：`1.0`

当前原型里的含义：

- 避免第一版结算在数据还很少时，过早出现完全锁死
- 同时允许强角色在准备充分时，内部概率先超过 `100%`，最后再收敛到 `100%`

影响方式：

- 截断

需要特别说明：

- 这仍然只是当前版本的保护性做法，不代表后续所有任务都应该轻易满概率
- 后续应尽量避免“玩家已经准备充分，仍然被固定底噪概率硬判失败”的烦躁体验
- 更合适的方向是：
  - 准备不足、高风险、信息缺失时，失败明显存在
  - 准备充分、人物合适、线索足够时，部分任务应能逐步趋近稳定成功
  - 真正严重的坏结果，不应主要由纯底噪随机直接决定

## 三、结果受到哪些因素影响

### 1. “谁接任务”

受这些影响最大：

- 人格
- 报酬
- 风险
- 任务性质
- 最近是否刚做过任务
- 资源偏好（仅限仍有资源目标的任务）

### 2. “任务会不会成功”

当前只对调查 / 异常任务生效，受这些影响：

- 危险性：越高越难
- 难度：越高越难
- 耗时压力：越高越难
- 未知度：越高越难
- 回传难度：越高越难
- 稳定性：越高越稳
- 线索数量：越多越容易
- 能力：越强越容易
- 少量人格：按任务类型和风险给轻修正

当前这套公式的设计目标不是“永远保留讨厌的低概率翻车”，而是：

- 先让准备程度、任务风险、人物匹配度开始真正影响结果
- 后续再逐步把不确定性更多放在“结果质量、耗时波动、回传完整度”上
- 而不是把重大坏结果长期主要绑定在一条固定底噪概率上

### 3. “任务给什么结果”

当前仍主要由模板决定：

- `resource`
- `lead`
- `discovery`

也就是说：

- 当前公式决定“成还是败”
- 结果类型本身还不是由公式动态推导的

## 四、哪些是线性的，哪些不是

### 当前主要是线性的

- 线索数量修正
- 长时任务惩罚
- 能力高低修正
- 多数人格修正
- 多数阈值高低修正

### 当前主要是分预算后的线性

- 危险性惩罚
- 难度惩罚
- 耗时压力惩罚
- 未知度惩罚
- 回传难度惩罚
- 稳定性修正
- 能力修正

### 当前主要是分段固定的

- 不同任务性质下的求知加成切换
- 不同隐藏特征下的人格修正

### 当前主要是截断 / 上限控制

- 成功率上下界
- 线索加成上限
- 报酬归一化范围

### 当前还没有正式用到的

- 反比例
- 指数变化
- 对数变化
- S 曲线

## 五、后续最可能扩的方向

- 线索数量不只影响成功率，也影响失败时回报质量
- 不同线索类型影响不同结算项
- 任务不再只有成功 / 失败，而有部分成功
- 伤病 / 失联 / 死亡进入结果层
- 同一套能力进一步进入更多任务类型

## 六、目前最值得你盯着看的地方

如果你后面觉得“某类任务还是太容易成功”或“某个人去做总是不合理”，优先看这些：

- `QUEST_RESOLUTION_TUNING.baseIntelSuccessChance`
- `QUEST_RESOLUTION_TUNING.totalPenaltyBudget`
- `QUEST_RESOLUTION_TUNING.dangerPenaltyShare`
- `QUEST_RESOLUTION_TUNING.challengePenaltyShare`
- `QUEST_RESOLUTION_TUNING.clueBonusPerIntel`
- `QUEST_RESOLUTION_TUNING.capabilityWeight`
- `QUEST_RESOLUTION_TUNING.personalityWeight`

如果你觉得“这个人为什么又接了这种任务”，优先看：

- `QUEST_ACCEPTANCE_TUNING`
- `QUEST_INTEREST_TUNING`

也就是说：

- `接不接` 看接取公式
- `成不成` 看结算公式

## 七、批量模拟工具

为了避免反复手动点页面测试，当前已经补了一份批量模拟工具：

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution
```

它会直接读取当前：

- `config/quests/resolution.json`
- `config/adventurers.json`

并输出每条结算测试任务的：

- 默认模式下的最小验证摘要
- `--full` 时的逐任务完整拆解

常用用法：

```bash
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --full --quest resolution-standard-advantage
conda run -p /home/windflying/Code/AdventureHouse/.conda-node npm run simulate:resolution -- --runs 5000 --intel-count 2
```

适合什么时候用：

- 想先看当前公式大概会导向什么结果
- 不想手动重复点很多轮任务
- 想对照某条任务在不同线索数量下的变化

这份工具当前服务于 `v0.9` 结算测试矩阵，不直接替代实际游玩感受，但很适合先筛掉明显不合理的参数。
