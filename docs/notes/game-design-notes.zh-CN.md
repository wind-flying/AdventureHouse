# Adventure House 设计备忘录

## 文档用途

这是一份当前游戏方向的本地备忘录。

目的不是写正式策划案，而是把现在已经说清楚的设计意图、关键词和未解决问题保存下来，避免后续开发时偏离最初想做的体验，也避免以后回头看时连自己当初想表达什么都不记得。

## 当前开发约定

为了避免后续功能增多后代码和文本越来越难整理，当前先定一条工程约定：

- 程序内部使用的标识，不等于玩家看到的显示内容
- 能放到配置层的内容，尽量不要写死在逻辑里
- 能放到文本层的内容，尽量不要散落在业务代码里
- 新增功能时，优先考虑拆出独立文件，让旧模块只负责调用和编排

这条约定的目的是：

- 避免 `wood`、`food` 这类内部字段直接出现在界面上
- 避免后续补市场、建筑、主线时又回头大面积搬代码
- 让以后改文案、改显示、改规则时，能分别在不同层处理

这是一条长期方向。现在项目里还没有把所有旧内容都彻底分离完，但后续新增功能默认要按这个标准写。

## 交互反馈原则

后续界面设计应尽量减少“先允许操作，再弹出提示说明失败”的做法。

更优先的策略应该是：

- 在操作前就让玩家知道当前能不能做
- 用禁用、置灰、缺失条件说明、状态标签等方式前置表达限制
- 把弹出提示更多留给意外结果、真正需要玩家确认的变化，或已经发生的系统反馈

这条原则尤其适用于：

- 任务不能重复发布
- 某个建筑或功能当前不可用
- 某个角色当前不接受这类互动

目的不是完全不用提示，而是尽量避免让玩家先点击、再被系统“驳回”。

## 边界样例与健壮性验证

后续除了写“正常功能样例”，也应保留一小组专门用于暴露边界问题的内容样例。

这些样例的目标不是给玩家体验完整任务线，而是故意验证系统在以下情况下是否还能稳定工作：

- 任务没有配置线索引用
- 任务失败时没有配置失败线索或失败摘要
- 某些文本缺失时是否会触发可读的兜底内容
- 开启条件是否可能写出不可达状态

这类样例应尽量单独归档在一个专门主题里，例如 `validation`，不要混进正常主题线。

这样做的价值是：

- 能尽早发现配置系统的缺口
- 能倒逼完善兜底逻辑和内容校验工具
- 能避免只靠“写对所有内容”来维持系统稳定

## 核心幻想

玩家不亲自去冒险。

玩家经营的是冒险者村庄中的一个据点，可以理解为店铺、委托中介、冒险者服务中心，或者几者的结合体。玩家通过发布任务、赠送物品、提供服务、经营关系和建设设施，去间接影响冒险者。

这个游戏的乐趣，应该主要来自：

- 影响一群有自己目标的人
- 看到延迟且不完整的结果
- 从零碎信息中推断局势并调整策略
- 不直接控制冒险，却能靠冒险者生态赚到钱并推动世界变化

## 玩家扮演什么角色

玩家不是全知全能的指挥官，也不是直接战斗的人。

玩家更像是：

- 村庄中负责经营和服务的人
- 机会的撮合者
- 原料和信息的处理者
- 与冒险者建立关系的人
- 在“村庄这一侧”尝试影响命运的人

## 信息获取规则

这是当前最重要的设计原则之一。

玩家不应该实时看到完整的冒险过程。玩家不应该拥有上帝视角，不能直接知道每一次战斗、每一次路线选择、每一个事件细节。

大部分“主线”信息，都应该来自玩家后来收集到的碎片，例如：

- 冒险者归来后的口头描述
- 伤势和装备损耗
- 书信、便条、记录
- 遗物和异常掉落
- 旅行者带回来的传闻
- 失败队伍留下的痕迹

但玩家仍然必须得到反馈。隐藏信息的目的应该是制造神秘感，而不是制造混乱。

所以当前规则可以总结为：

- 不给实时完整信息
- 不保证每次都有完整报告
- 但可以给延迟的、片段化的、带偏差的反馈

## 核心循环

1. 玩家经营一个村庄据点，先保证基本现金流和运营能力。
2. 玩家发布任务、提供服务、送礼、经营关系。
3. 冒险者根据报酬、性格、当前需求、风险倾向和关系远近决定接不接任务。
4. 冒险者离开，冒险过程发生在画面外。
5. 他们回来时可能带回材料、故事、伤病、线索，也可能什么都没有。
6. 玩家根据这些碎片重新判断局势，调整下一步的经营与引导方向。

## 冒险者应该是什么样的

冒险者不是机器人，他们必须有自己的行动理由。

可能的动机包括：

- 谋生
- 追求荣耀或危险
- 偿还债务
- 为个人目标筹钱
- 收集知识
- 追逐传闻、复仇、地位

他们接下玩家的任务，不应该只是因为“这是系统指令”，而更应该是因为这个任务和他们原本想做的事情有重合，或者至少对他们来说划算。

## 冒险者属性分层

后续建议把冒险者属性分成两层，而不是混成一大张面板。

### 1. 人格属性

这层优先服务于：

- 接不接任务
- 喜欢什么类型的任务
- 是否稳定合作
- 是否容易受关系影响

这层属性不应该直接完整展示给玩家，而更适合隐藏在内部，用“标签、印象、行为倾向”间接表现。

当前建议优先使用少量高价值人格轴：

- 勤勉
- 勇敢
- 逐利
- 社交
- 审慎
- 求知
- 纪律
- 韧性

### 2. 冒险能力属性

这层以后再展开，主要服务于：

- 任务成败
- 耗时
- 风险承担
- 伤病
- 收获质量

例如以后可能会有：

- 生存
- 采集
- 探索
- 战斗
- 交涉

当前优先级低于人格属性，不需要先做全。

## 属性设计约束

后续正式扩充冒险者属性和任务隐藏特征时，应尽量遵守一条约束：

- 不能存在“没有特点、只是重复别人的弱化版本”的属性

更具体地说：

1. 每个属性都应该至少有一个“主场公式”
   - 也就是至少有一类公式里，这个属性应当是高权重决定因素之一
   - 不要求它是唯一决定因素，但它必须在某个场景里有明显存在感

2. 如果某个属性没有自己的主场公式
   - 那它就只能作为通用修正项存在
   - 也就是对多类公式都稳定、均匀地产生影响
   - 这种属性可以有，但数量应非常克制

3. 不应长期让两个属性完全共享同一个主场
   - 如果两个属性始终只在同一类公式里做近似作用，它们就很容易重叠
   - 这会导致参数变多，但角色特点并没有变清楚

这条约束的目的不是强行减少属性数量，而是避免：

- 属性表越来越长，但很多属性没有清晰存在理由
- 所有属性都只是在所有公式里弱弱参与，最后谁都不鲜明
- 参数变多了，但玩法判断反而没有变得更有层次

后续可以接受：

- 一个公式有多个决定因素
- 一个属性在多个公式里都有影响

但不能接受：

- 某个属性既没有主场，也没有明确的全局用途

也就是说，后续新增属性前，应先回答：

- 这个属性最主要在哪一类公式里发力？
- 如果不是主场属性，它是不是至少能作为稳定的全局修正？
- 如果两者都答不上来，就不应该新增这个属性

## 人格与能力的关系原则

后续人格层和能力层不应被理解成两套完全独立、互不影响的参数。

更合理的方向是：

- 能力更偏向“客观上做不做得到”
- 人格更偏向“主观上怎么看待自己做不做得到”

这意味着后续很多公式里，人格不一定只是单独加减一项固定分值，也可以影响角色如何解读：

- 自己的能力
- 任务的风险
- 任务的报酬是否值得
- 未知信息是否会让自己退缩

这条原则的重点是“关系成立”，不是现在就把某一种具体乘法或加法公式定死。

也就是说，后续设计时可以接受：

- 人格直接影响任务意愿
- 能力直接影响任务结果
- 人格再进一步影响角色对自己能力和任务风险的主观评估

但当前不应把某一个示例公式，误当成最终定稿。

## 队伍与协作方向

后续不应把冒险者长期限制成“单人接任务”的模型。

更符合当前游戏方向的做法是：

- 有些任务天然适合单人
- 有些任务建议双人或多人
- 队伍人数并不是简单地“人多就一定更快”
- 队伍的价值更多体现在安全性、稳定性、信息回传完整度，以及某些阶段的效率

后续队伍来源可以包括：

- 临时随机组队
- 因任务需求临时凑队
- 关系好的人自然结伴
- 长期固定搭档或固定队伍

这样做的好处是：

- 冒险者之间不再彼此孤立
- 失败时可以出现“部分归来、部分失踪、有人带回残缺消息”的反馈
- 固定队伍本身也可以成为长期叙事来源

当前这部分只记录为后续方向，不在当前版本实现。

## 任务时间与回报节奏方向

后续任务耗时不应继续简单理解为“固定天数倒计时”。

更合理的结构应至少拆成：

- 固定耗时
  - 例如赶路、等待、搜索、返程
- 可变耗时
  - 例如战斗、采集、侦查、突发事件处理
- 波动项
  - 例如意外拖延、路线变化、遭遇事件

也就是说，任务总耗时以后更适合理解成：

`总耗时 = 固定耗时 + 可变耗时 + 波动`

同时，“完成任务”也不应该直接等于“立刻回到玩家面前交付结果”。

更自然的阶段应包括：

- 接任务
- 出发
- 执行
- 返程
- 玩家得知结果

这能更好地支持：

- 神秘感
- 延迟反馈
- 不完整消息
- 部分归来的失败结果

当前这部分同样只记录为后续方向，不在当前版本实现。

## 任务类型意愿与实例修正方向

后续任务承接不应长期只按“每一张任务单独重新算一次意愿”处理。

因为当同一天挂着多张同模板任务时，如果系统完全逐实例独立判断，就可能出现这种观感问题：

- 同样是木材补货
- 前一张不接
- 后一张又接
- 玩家却很难感知两者到底差在哪

从数据上看，这些任务仍然应被视为不同实例，因为它们可能有不同的：

- 数量
- 报酬

## 任务认知层更新方向

后续当冒险者带回对任务的新判断时，不应优先通过“复制很多任务变体”来表达差异。

更合理的结构应该是：

- 任务本体相对稳定
  - 任务模板
  - 当前阶段
  - 结果去向
  - 可重复规则
- 玩家对任务的认知逐步更新
  - 当前已知风险
  - 当前已知异常程度
  - 当前已知建议人数
  - 不同冒险者给出的观察记录

也就是说，后续应优先让冒险者影响“玩家对任务的理解”，而不是频繁改写任务本体。

这样做的好处是：

- 不会因为不同反馈而复制出大量近似任务模板
- 更符合“不同人对同一件事会有不同判断”的碎片叙事
- 后续更容易扩展可靠度、来源、时间差、主观看法等内容

这条原则会影响：

- 消息板
- 调查任务后续
- 任务详情展示
- 失败反馈与风险修正
- 预估耗时
- 后续附加条件

## 随机线索重复策略方向

当前随机线索池还是纯随机，所以已经获得过的线索仍可能再次出现。

后续更合理的方向不是简单做成“绝不重复”，而是根据线索类型采取不同重复策略：

- 传闻类线索
  - 允许重复出现
  - 重复时追加“旧闻再提”的补充语
- 重要线索
  - 更适合优先未获得
  - 重复次数应更少
- 发现类记录
  - 通常更偏唯一
  - 不宜长期重复掉落

线索对象后续可逐步支持：

- 多条文本
- 重复获得时的追加语
- 最大出现次数

这样可以同时保留：

- 碎片叙事的反复听闻感
- 重要线索逐步收集的推进感
- 随机池不会太快失去作用

但从人物行为的稳定性来看，后续更合理的做法应是分两层：

1. 对任务类型的基础意愿
   - 例如某人今天整体上就不太想接“普通补货类任务”
   - 或对“调查 / 异常类任务”整体更感兴趣

2. 对具体任务实例的修正
   - 在已经有基础意愿的前提下，再根据数量、报价、耗时等具体参数微调

也就是说，后续可以理解成：

`总接取意愿 = 对任务类型的基础意愿 + 对具体报价/数量/耗时的修正`

这样做的目标是：

- 让人物对同类任务的态度更稳定
- 保留不同报价和数量仍然会影响决策的空间
- 避免同模板任务在同一天呈现过强的“像掷骰子一样”的不一致感

当前这部分先记录为后续任务系统优化方向，不在本轮直接实现。

## 任务特征维度方向

后续如果想让冒险者倾向真正成立，不能长期只让任务提供少数几个输入，例如：

- 风险
- 性质
- 报酬
- 耗时

因为这样会导致很多不同人格虽然名字不同，但实际上都在看同一小组任务标签，最后人物差异会被压扁。

更合理的方向，是逐步为任务补足“行为特征维度”，让任务能更完整地表达“这到底是一份什么样的活”。

后续值得考虑的维度包括：

- 危险性
- 稳定性
- 新奇度 / 异常度
- 纪律要求
- 社交 / 公开性要求
- 长线压力 / 体力压力
- 收益吸引力
- 道德负担 / 灰色程度

这样后续就能形成更自然的映射，例如：

- 勇气 -> 危险性
- 审慎 -> 危险性 + 稳定性
- 求知 -> 新奇度 / 异常度
- 纪律 -> 稳定性 + 纪律要求
- 社交 -> 公开性 / 协作需求
- 韧性 -> 长线压力
- 逐利 -> 收益吸引力
- 勤勉 -> 重复劳动 / 基础工作权重

这条方向的重点不是立刻加很多字段，而是明确：

- 后续任务系统应先补“任务特征输入”
- 再让人格系统映射到这些输入
- 避免长期用少数枚举标签硬撑完整人物差异

## 运营委派与管理递进方向

后续可以考虑采用递进式增量，而不是让玩家一开始就像成熟经营者一样同时操控所有系统。

更合理的节奏可能是：

- 前期：玩家亲自处理少量关键运营事务
- 中期：通过关系、信任和人手逐步把重复劳动委派出去
- 后期：玩家更多负责拍板与调度，而不是亲手处理所有细碎工作

适合逐步开放委派的内容例如：

- 每日补货委托发布
- 餐馆基础营业
- 基础收购和整理
- 日常库存维护

但核心战略决定不应被完全自动化，例如：

- 本周重点投入哪类资源
- 是否调查某个异常地点
- 是否开放新设施
- 是否把关键人物留在据点而不是外出

这条方向的重点不是“强制玩家前期打工”，而是：

- 前期只有少量事情必须亲自决定
- 后期通过信任和组织能力逐步解放管理负担
- 委派本身成为成长的一部分

## 非现金奖励与据点独占价值

后续不应让所有任务奖励都只剩下金钱。

尤其是引导型任务、特殊委托和高关系任务，更适合加入一种只有玩家据点能提供的非现金价值，例如：

- 村中声望
- 委托信誉
- 人情
- 推荐资格
- 线索优先权
- 完成记录或正式证明

这样玩家的价值就不只是“出钱的人”，而是：

- 机会的撮合者
- 信用的中介
- 能提供长期回报的人

这里要注意，后续如果采用“人情、信誉、声望”这种奖励，它们必须被玩家清楚识别成系统收益，而不能伪装成普通对话文本。

## 关键信息高亮原则

虽然整体叙事应保持碎片化和非上帝视角，但关键信息不能完全依赖玩家自己从大段文本里手动辨认。

后续涉及下面这类内容时，应考虑明确高亮、换色、图标或标签提示：

- 主线碎片
- 重要线索
- 新解锁的关系变化
- 非现金奖励
- 人情、信誉、声望等特殊收益
- 只出现一次的重要传闻

也就是说：

- 可以保持碎片叙事
- 但不能把真正重要的系统信息埋没成普通叙述文本

例如以后如果出现：

- “某人欠你一个人情”
- “你获得一份推荐资格”
- “这条消息属于关键线索”

就不应只当成一句普通对话显示，而应明确提示玩家：

- 这是一类奖励
- 这是一条关键发现
- 这会影响后续玩法

## 关系系统定位

关系的作用应该是增加影响力，而不是让冒险者失去自主性。

可以先按这样的层次理解：

- 陌生人：只能通过公开任务互动
- 熟客：更容易接受适合自己的任务
- 信赖对象：可以接受定向委托，也能进行更私人化的互动
- 核心伙伴：建立长期合作，玩家对其行为有更强影响力，也能获得更详细反馈

这里要强调的是，高好感不应该让角色变成“无条件服从的员工”。更合理的效果应该是：

- 玩家更容易接触到他们
- 玩家说的话更有分量
- 玩家能优先获得合作机会
- 玩家能谈成别人谈不成的安排

## 成长设计原则

冒险者的成长必须存在取舍。

玩家不应该能把每个冒险者都培养成全能角色。这个游戏想坚持的方向不是“你必须先这样才能那样”，而是“你可以选择这样发展，也可以选择那样发展”。

这意味着：

- 成长路线应该有分支
- 投入应该迫使玩家做选择
- 强项应该伴随弱项，或者至少伴随机会成本
- 礼物和支持更多是引导，而不是完全决定成长结果

另外，冒险者并不只是被玩家单向塑造。他们也会自己经营自己，例如：

- 自己决定钱怎么花
- 自己偏好什么装备
- 自己决定更愿意接什么工作
- 自己选择想过怎样的生活

## 任务类型

目前可以先把任务分为两大类。

### 1. 经营型任务

这类任务更接近日常补货和基础经营。

例如：

- 砍木头
- 采药草
- 带回食材
- 送来常见材料

作用：

- 维持库存
- 给店铺和建筑提供原料
- 稳定村庄的基础经济
- 支撑玩家最基础的现金流

### 2. 引导型任务

这类任务更接近“影响行为”和“推动主线碎片收集”。

例如：

- 优先探索某片区域
- 调查一条传闻
- 护送某位学者
- 避开某条高风险路线
- 搜寻失踪小队的踪迹

作用：

- 引导冒险者行动方向
- 推动主线以碎片形式展开
- 让玩家在不直接控制冒险的前提下仍然能够施加策略影响

## 冒险者为什么要接玩家的任务

这是整个经济逻辑能不能成立的关键。

如果冒险者自己去做一件事，能赚得更多，那玩家发布的任务就必须在别的地方提供价值。任务奖励不能只理解为“付给冒险者的劳动工资”，而应该是玩家提供的一整套便利和保障。

玩家据点能提供的价值可以包括：

- 立刻到手的现金
- 更省事的出售渠道
- 稳定买家
- 帮冒险者承担一部分风险
- 食物、治疗、住宿、修理、工具等配套服务
- 人情和信任关系
- 后续更好的合作机会

所以玩家的价值不应该是“只有玩家能处理这些东西”，而应该是“玩家更擅长把这些冒险收获转化为稳定而更高价值的结果”。

可以压缩成一句话：

冒险者把世界里的机会带回来，玩家把这些机会加工成更稳定、更高附加值的经营成果。

## 玩家经营系统为什么必要

如果玩家只能一直花钱雇人，那整个循环就会变成“不断赔钱养别人”，这会让游戏很快失去动力。

因此玩家必须拥有自己的经营杠杆。玩家的据点应该能做到：

- 收购或接收原料
- 把原料加工成更值钱的商品
- 提供冒险者自己不方便高效完成的服务
- 靠设施、物流、客流和信息差赚钱

前期可以有的基础设施：

- 小饭馆或餐食柜台
- 公告板
- 仓储和采购能力

后期再逐步扩展为：

- 医馆
- 铁匠铺
- 旅店
- 情报据点

这些建筑不应该只是单纯的赚钱按钮，而应该服务于核心体验：玩家在不亲自冒险的情况下，通过经营与关系影响冒险者并从中获利。

## 主线推进方式

“主线”不应该像传统任务日志那样一开始就写清楚，而应该更多通过碎片被玩家慢慢拼出来。

玩家最开始可以知道一两个明确钩子，但后续更多内容应该来自：

- 冒险者归来后的报告
- 异常任务结果
- 遗物
- 失踪事件
- 市场异常
- 多次提到同一地点、势力或事件的零散信息

这样玩家会更像是身处这个世界的人，而不是站在世界外读剧情的人。

## 关于重开 / 传承

这一点目前还没有定案，但当前方向应该尽量避免那种“完全硬重置”的设计，因为那会直接削弱玩家对具体冒险者的感情投入。

更适合的可能是：

- 村庄传承
- 时代推进
- 遗产系统
- 短期资源重置，但长期认知与地位保留

可能会重置的东西：

- 金钱
- 库存
- 当前合同和悬赏
- 短期市场状态

可能部分保留的东西：

- 声望
- 建筑蓝图
- 已发现的情报
- 遗物收藏
- 知名冒险者记录

## MVP 边界

第一版可玩的目标，不是把整个世界做完，而是验证这个核心幻想到底成不成立。

推荐的第一版范围：

- 少量但有明显差异的冒险者
- 基础关系值
- 经营型任务
- 引导型任务
- 一个核心经营建筑
- 一条简单的“原料 -> 商品 -> 金钱”转化链
- 冒险归来后的片段化反馈

前期应避免做得太早的内容：

- 完整市场模拟
- 很深的通信系统
- 复杂重开循环
- 大规模人口模拟
- 同时塞太多建筑

## 首个完整版本目标

当前可以把“第一个完整版本”理解为：

玩家在一个村庄据点中，逐步认识、影响并培养一批冒险者；他们会成长、接触神秘冒险、成为村庄的重要人物，并最终走向退休、老去、战死或失踪。玩家能通过日志、纪念记录、墓地等方式见证并保存他们留下的痕迹。

这一版更强调：

- 见证具体人物的一生
- 看到他们从普通人变成村庄支柱
- 接触神秘冒险带来的碎片信息
- 接受有人会离开、老去、战死或失踪
- 让玩家留下“这些人存在过”的记忆载体

这版完成后，玩家应能对某些具体冒险者产生明确记忆，而不是只记得自己经营过一套系统。

## 墓地与去向记录

后续如果角色离场，不应该只是从系统中消失。

更合适的做法是记录他们的去向，例如：

- 墓地
  - 用于确认死亡、战死、病故者

- 返乡或远行记录
  - 用于退休、离村、归乡者

- 失踪记录
  - 用于下落不明、未归者

这样玩家才能真正感受到人物命运，而不是名单长度发生变化。

## 圣堂与地下交易系统

“圣堂”这类暗杀、驱逐、匿名悬赏、解除悬赏、追查幕后发布者的系统方向是成立的，但当前不建议放进首个完整版本。

原因是这套内容会额外引入：

- 地下任务系统
- 匿名悬赏规则
- 角色立场与仇恨
- 调查与反制
- 更复杂的死亡归因和后果

这更适合作为第二阶段的大型扩展内容，而不是首个完整版本的必要组成。

当前边界建议是：

- 初版完整目标：见证冒险者成长、成名、离场与留下痕迹
- 后续扩展目标：再引入更黑暗、更社会化的地下交易与清算系统

## 当前仍未定的问题

- 长期目标最清晰的表达应该是什么？
- 冒险者在花钱和自我发展上应保留多大自主权？
- 玩家最低需要知道多少信息，才能既不失去神秘感，也不至于没法做决策？
- 失败的代价应主要体现在哪些方面：亏钱、受伤、失踪、关系破裂、声望受损？
- 需要多少个有名字、会反复出现的冒险者，关系玩法才会真正成立？
- 传承或重开到底应该怎么做，才能既提升后续效率，又不抹掉情感积累？

## 当前工作原则

- 玩家能影响，但不能完全指挥。
- 世界应该因为角色有各自目标而显得是活的。
- 神秘感是好的，但不能让反馈缺失到无法判断。
- 成长必须有取舍。
- 经济系统是为了支撑关系和任务循环，而不是反过来抢走重点。
- 新系统必须叠加在核心幻想上，不能变成互不相关的小玩法集合。

## 主线内容组织与开启原则

后续主线内容不应继续长期堆在单一任务文件里。

更适合当前项目的做法是：

- 保持统一的任务模板骨架
- 按主题拆分任务内容文件
- 例如：
  - `base`
  - `forest`
  - `river`
  - 以后还可以扩到 `mine`、`church`、`north-road`

目标是让后续“新增一条主线”尽量变成：

- 新建一个主题文件
- 在里面补这条线的任务模板、开启条件、文本和备注
- 尽量不要回头改底层逻辑代码

这条原则的前提是：

- 所有主线沿用统一接口
- 任务模板结构保持一致
- 条件表达统一，而不是每条线各自发明一套规则

主线开启方式也不建议做成纯线性“上一条完成，下一条固定出现”。

更符合当前游戏方向的方式是：

- 底层用条件驱动
- 表现层仍保持碎片叙事

也就是说，系统可以根据条件决定任务是否可见，但玩家实际感受到的更像：

- 某条消息变得可继续跟进
- 某个熟客带回了新的说法
- 公告板上出现了新的异常委托
- 某个旧调查突然有了回音

后续建议逐步支持的开启条件接口包括：

- 某任务成功
- 某任务失败
- 收到某类线索
- 收到某类发现
- 认识某位冒险者到特定阶段
- 某建筑或据点条件满足

当前不必一次实现所有条件，但接口方向应先统一，避免后面为了省事一路写成线性主线树。

## 文本字段标准方向

后续任务、线索、发现、结果反馈这类文本，建议逐步统一成“单条文本或文本数组都能被同一套接口接收”的结构。

目标是让后续写内容时可以自然从：

- 单条文本

过渡到：

- 多条随机文本

而不需要因为“这个地方原来只支持字符串”就回头改业务逻辑。

长期标准建议是：

- 业务逻辑层不关心这是单条还是数组
- 文本层统一负责抽取一条可显示文本
- 新增内容时，尽量优先考虑这种可扩展写法

当前项目里这套规则还没有完全统一，所以这是“应逐步推进的标准方向”，不是“已经全项目实现完毕”的现状。

## 线索库方向

后续线索不应长期只作为消息板里的普通记录存在。

更长期的目标是让线索逐步成为独立内容对象，也就是形成“线索库”：

- 任务可以产出某条线索
- 线索可以沉淀在消息板/线索板
- 线索可以作为后续任务的开启条件
- 线索也可以拥有自己的文本、状态和阶段

当前这部分仍属于后续结构升级方向，不要求立即实现，但应作为任务结果系统下一阶段的重要目标。

## 线索驱动任务方向

后续线索不应只承担“解锁一下任务”的单一作用。

更适合当前游戏方向的做法是：

- 线索可以作为开启条件
- 线索也可以作为任务参数修正来源
- 线索在完成阶段性用途后，可以进入“已处理 / 已归档 / 已隐藏”的状态

后续可支持的情况包括：

- 任务 1 可能带回线索 1 / 2 / 3 中的任意一条
- 只要其中任意一条出现，就能开启任务 2
- 但玩家掌握的线索越多，任务 2 的已知信息、稳定性或后续结算参数就越明确
- 当任务 2 完成后，旧线索可被标记为已处理，避免消息板长期堆满仍在“活跃”的旧信息

这条方向的重要原则是：

- 线索既可以是“开门条件”
- 也可以是“任务认知与任务参数的修正来源”

当前不要求立即把这整套做完，但后续实现时应优先按这个方向推进，而不是把线索长期当作一次性的文本奖励。

## 协作约定补充

后续每次准备开始一个新功能前，应先对照文档检查两件事：

- 之前讨论过的设计是否已经写进对应文档
- 当前准备实现的内容，到底是“已确定方向”还是“还只是讨论想法”

目的不是拖慢开发，而是避免：

- 设计已经讨论过，但没有留档
- 代码先实现了，文档却落后很多
- 后续回看时分不清哪些是已经确认过的方向，哪些只是当时顺口提到的想法

## 内容校验工具方向

随着任务、线索、主线条件逐步转向人工编辑的配置文件，后续应考虑补一个轻量的内容校验工具。

它的目标不是替代设计，而是帮助人工编辑时尽早发现常见错误，例如：

- 任务 `id` 重复
- 线索 `id` 重复
- 任务引用了不存在的 `resultIntelId / failureIntelId`
- `unlockConditions` 里写了不存在的任务或线索
- 线索从未被任何任务引用
- 某个任务可能永远不会被解锁
- 测试字段和正式内容混用得不合理

这类工具后续更适合做成：

- 本地可执行
- 输出文件名和问题位置
- 作为人工扩内容时的辅助检查手段

当前不急着实现，但这是后续“配置驱动内容”阶段很值得补的一项基础工具。

## 长列表展示方向

随着游玩时长增加，日志、消息板、历史任务等列表会不断积压。后续不应长期采用“把所有历史记录一次性完整渲染到页面”的方式。

更合适的方向是：

- 默认只展示最近一段内容
- 更旧的内容通过“加载更多 / 展开更多”按需查看
- 优先减少首次渲染和常驻 DOM 数量
- 真到内容量明显增大时，再考虑更重的滑动窗口或虚拟列表方案

也就是说，后续更推荐先做“按需展开的长列表”，而不是一开始就上复杂的虚拟滚动。

## 当前补充记录

- 当前任务系统、冒险者偏好和资源配置使用的是同一批资源 id，后续市场与材料系统应直接复用这套资源定义，而不是另起一套命名。
- 当前冒险者偏好在界面上仍直接显示内部 id，例如 `wood`、`food`，后续应补一层面向玩家的文本映射。
